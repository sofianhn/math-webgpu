Teaching a browser to do arithmetic (badly, then better)

What the model trains on, what the parameter tables count, why three-digit inputs fail, and when arithmetic would become “intrinsic.”

You hit Train, watch loss fall, then try an expression. Charts help. But two questions keep coming up: what are those parameter bars counting, and what data is this thing actually training on?

What data it trains on

Each training row is a random expression with operands a, b ∈ {0…99} (two digits), an operator in {+, −, ×, ÷}, and a target integer answer. Huge products are resampled so answers stay in classes 0…999.

The live data feed on the demo shows rows like 12 + 34 = 46 · features a=1|2 op=+ b=3|4 → class 46 so you can see the human expression and the feature breakdown.

Place-value features (not a flat ID)

Each operand is split into tens and ones one-hots (10+10), plus 4 operator slots, for both sides → 44 input features. So 23 and 27 share “tens = 2”. That is a tiny step toward structure — still not an addition algorithm. The last layer is a softmax over answer classes, not a calculator.

What the parameter tables are

Learning rate / epochs / batch / hidden size are hyperparameters (how optimization runs). W1, b1, W2, b2 are the model parameters — the arrays of numbers being updated:

TableMeaning
W1weights from input features → hidden units
b1bias per hidden unit
W2weights from hidden → answer classes
b2bias per answer class

Bar length = L2 magnitude before → after a run. Count = how many numbers live in that table. Together they are the network’s memory, not the training schedule.

Why 100 + 3 will not be fixed by more epochs

The encoder only has tens and ones places. 100 needs a hundreds place that does not exist. Extra epochs only revisit 0–99. That is a representation problem (OOD), not a learning-rate problem.

At what point would it learn intrinsically?

Short answer: not with this setup alone — even at 100% train accuracy.

This model is trained as input pattern → answer class. It can memorize many maps. Place-value features may reuse digit patterns, but the loss never asks it to execute addition — only to name the right class.

You get closer to intrinsic arithmetic when:

  1. Representation forces composition (digit outputs, binary, relational magnitudes) and you test numbers never seen in training.
  2. Supervision teaches a procedure (scratchpads / chain-of-thought / tools), not only the final integer.
  3. Architecture can run algorithms (sequence models over digits, program induction), then you measure length/digit generalization.

Classroom test: hold out all ones-digit 7s, then probe 17 + 2. Collapse ⇒ memorized surface patterns. Stable digit-like errors ⇒ maybe proto-rules. This demo’s classifier still will not invent a hundreds place for 100.

Making it learn math (not just memorize)

  • Digit-wise answer head: predict hundreds / tens / ones, compose 100·H + 10·T + O — not a flat 1000-way table.
  • Fair expression holdout: freeze ~10% of exact expressions for eval, but keep every digit 0–9 in other training rows. (Ones-digit-7 holdout was a harsh probe that never activated that input feature.)
  • Watch train vs held-out accuracy: both rising ⇒ digit generalization; only train rising ⇒ still overfitting combinations.

What to try

  1. Train Medium + Default with fair held-out on; watch hold accuracy climb.
  2. Probe a train-dist sum and a frozen held-out expression from the bank.
  3. Try 100 + 3 (OOD) — still no hundreds input place.
  4. Check parameter tables for Wh / Wt / Wo, not a giant W2.

A model only learns the world you can represent — and only the objective you optimize.
